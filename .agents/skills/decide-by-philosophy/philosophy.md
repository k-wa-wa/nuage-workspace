# k-wa-wa の哲学

技術に関する判断の評価軸。

## なぜ技術をやるのか

- 仕組みを作ること自体が面白い
- 自分が作ったものが動くのが面白い

## 美しいと思うもの

- 宣言的であること
- 冪等であること
- GitOps や IaC のように、あるべき状態を書けばそのとおりになる仕組み
- コンポーネントごとの責務がはっきりと分かれていること。システム単位からコード単位まで、責任と役割が明確に分離されていること

## 嫌いなもの

- 冗長なもの、無駄なもの
- 手作業が必要なもの
- 統一感がないもの

## 判断の傾向

ルールではなく傾向。ケースバイケースで変わるので、理由と、ひっくり返る条件を見て、今回の状況に当たるかを判断する。

| 迷うところ | 基本の傾向 | 理由 | ひっくり返る条件 |
| --- | --- | --- | --- |
| 自前で構築・運用するか、マネージドサービスを使うか | 自前で持つ | ・仕組みを作って動かすこと自体が面白いから<br>・外部サービスへの依存を増やしたくない、宣言的に定義しづらい | 運用することに面白さがない周辺の領域。自前では必要な信頼性を確保できないとき。その他メリットが大きいとき |
| 早く動かすか、綺麗に作るか | 急がない個人開発なら、綺麗な設計を目指す | 急ぐ理由がなければ、技術検証・個人的な興味として綺麗な状態を目指したい | 期限があるとき。試して捨てる検証のとき |
| 新しい技術か、枯れた技術か | 新しい技術 | 触ること自体が面白く、学びにもなるから | 長く保守する対象で、情報が少なくて詰まりやすいとき |
| 障害対策や品質をどこまでやるか | できるだけ完璧にする | あるべき状態を保てる、冪等で宣言的な仕組みを美しいと思うから | 使い捨ての検証。品質を上げるコストが得られる価値を明らかに上回るとき |
| 手作業か、自動化か | 自動化する | 手作業が必要なものが嫌いだから。手作業を忘れると詰むから | 自動化のコストが、手作業の総量を明らかに上回るとき |
| 宣言的に書くか、手続きで書くか | 宣言的に書く | あるべき状態を書けばそのとおりになる仕組みが美しいと考えるから | 宣言的に表せない処理のとき |
| 設定や秘密情報をどこで管理するか | Git を起点に管理する。秘密情報は暗号化して Git に置く | 状態と変更の経緯が Git に残り、統一感が出るから | 鍵そのものなど、Git に置けないもの |
| ドキュメントと判断の記録をどうするか | 日本語でしっかり書く。役割を分けて書き、設計判断の経緯（検討事項と結論）を残す | 後から理由をたどれるようにし、統一感を保つため | 一般的な判断、ベストプラクティス通りのもの、記載することで逆にノイズになるものは記載しない |
